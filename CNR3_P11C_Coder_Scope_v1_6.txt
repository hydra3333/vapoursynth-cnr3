1. THE THREE-CATEGORY CHECKPOINT RULE (read carefully -- do NOT conflate)
--------------------------------------------------------------------------------
There are THREE fresh-start frame categories, governed by DIFFERENT rules. P.11C
must treat them distinctly:

(1) DETECTED-CUT frame K (first frame of a NEW scene):
    - reached via a NORMAL RECURSIVE compute -- it HAS a predecessor (output[K-1]);
    - the detector runs (current source K vs previous filtered K-1), returns "cut";
    - output[K] computed as fresh-start (chroma-copy, chain severed) AND STORED WITH
      THE CHECKPOINT FLAG SET. CMS 6.4 / 9.2. *** P.11C WIRES THIS -- it is the core
      of the phase. A scene change MAKES THE NEW FRAME A CHECKPOINT, via detection. ***

(2) FRAME 0:
    - no predecessor exists -> detection CANNOT run (nothing to diff);
    - fresh-start for STRUCTURAL reasons;
    - IS a checkpoint, but by the §6.3 GRID rule (frame 0 always grid checkpoint),
      NOT by detection. P.11C does not touch this.

(3) BOUNDED-SEARCH FLOOR (max(0,N-B)):
    - no in-window predecessor -> detection CANNOT run;
    - fresh-start for STRUCTURAL reasons;
    - checkpoint only if it lands on the §6.3 grid; not made a checkpoint by detection.

DETECTION-NOT-APPLICABLE applies to categories (2) and (3) ONLY -- the structural
fresh-starts with no predecessor to detect against. It does NOT touch category (1).
P.11C wires detection ONLY at live recursive computes that HAVE a valid previous
filtered output: branch-c target, branch-d hole computes, branch-d target.
(No CMS change -- this is CMS-consistent per §1/§6.3/§6.4; recorded as a scope boundary.)

2. SCOPE ITEMS (what to build)

S1. LIVE SCENE-CHANGE CONFIG (per-instance).
    - Add/populate Cnr3SceneChangeConfig {scene_change_threshold:int64, scene_chroma:bool}
      in INSTANCE/FILTER DATA (not a compile-time flag), so later plugin parameters can
      feed it without rewiring the live path.
    - P.11C live defaults: scene_chroma = false (luma-only; safer first default for a
      chroma denoiser on noisy analogue chroma).
    - THRESHOLD DERIVATION -- use the VERIFIED vsCnr2 formula (NOT an invented width*height
      proxy). The SEMANTIC SENSITIVITY SCALAR is scdthr (matching CNR2 terminology). P.11C stores it
      internally / defaulted per instance; EXPOSING it as a plugin parameter is DEFERRED to the
      later option-surface phase (do not add a plugin parameter in P.11C). The internal int64
      scene_change_threshold is derived from scdthr as vsCnr2's diff_max (VERIFIED against the
      vsCnr2.cpp source, Asd-g/AviSynth-vsCnr2, 2026-06-27):
          diff_max = (int64)((scdthr * full_w * full_h * max_pixel_diff) / 100.0) << (depth - 8)
          max_pixel_diff = scene_chroma ? ((219 + 224*2) >> (sub_sampling_w + sub_sampling_h))
                                        : 219
      *** CRITICAL: full_w, full_h are the FULL-FRAME (LUMA) dimensions -- vsCnr2 uses
      vi.width * vi.height -- NOT the chroma-grid dimensions. *** The accumulation loop runs over the
      CHROMA grid accumulating abs(luma_diff) << (subw+subh) per sample; that per-sample shift is what
      reconciles the chroma-grid accumulation with the full-frame w*h in the threshold. Using chroma-
      grid w*h would make diff_max 4x too small for 4:2:0 (over-sensitive -> false cuts). [An earlier
      handover note said "chroma-grid dimensions" -- that was WRONG; corrected here against the source.]
      Operator-precedence note (do NOT "fix"): in vsCnr2 the expression is
      `(!scenechroma) ? 219 : (219 + (224*2)) >> (subsw+subsh)` -- `>>` binds tighter than `?:`, so the
      shift applies ONLY to the scene_chroma branch; luma-only is bare 219. Reproduce exactly.
      Decision-equivalent to vsCnr2: our detector is per-SAMPLE early-stop, vsCnr2 per-ROW, PROVEN
      identical (diff_total monotonic). depth = bits_per_sample.
    - DEPTH-SCALING ACCURACY -- RESOLVED (coordinator, 2026-06-27): apply the MOST-ACCURATE method,
      consistent with the P.2A parameter-scaling decision. The threshold derivation does NOT reproduce
      vsCnr2's integer-factor <<(depth-8); instead it scales PROPORTIONALLY with round-to-nearest, the
      same family as P.2A's (value*peak+127)/255. Concretely, the 8-bit-domain base
          base = (scdthr * full_w * full_h * max_pixel_diff) / 100      (kept full-precision through the scale)
      is scaled to native depth by the PROPORTIONAL factor peak/255 (peak = (1<<depth)-1), round-to-nearest:
          scene_change_threshold = (int64)( (base * peak + 127) / 255 )       [round-to-nearest]
      RATIONALE / governing-rule classification: vsCnr2's <<(depth-8) is a pure power-of-two depth scale
      that is identical to the proportional factor ONLY at 8-bit; it diverges at 10/12/14-bit AND at 16-bit
      (e.g. 16-bit: <<8 = x256 vs proportional x257). It is therefore an ACCIDENTALLY-LOSSY integer-factor
      artefact (the SAME family as peak/255, and in fact slightly more lossy since it is not even exact at
      16-bit), so the governing rule's "upgrade where accidentally lossy" applies. CONSEQUENCES: (a) at
      8-bit -- the only depth currently proven -- this is IDENTICAL to vsCnr2 (changes nothing today);
      (b) it is a DELIBERATE, RECORDED divergence from vsCnr2 at 10/12/14/16-bit (CNR3's scene-detection
      sensitivity is proportionally correct rather than power-of-two-coarse). This is consistent with CNR3
      being a faithful CORRECT redevelopment, not a byte-clone. Add to the recorded vsCnr2 deliberate-
      divergences list alongside the P.2A parameter-scaling entry.
      IMPLEMENTATION NOTES: keep the base full-precision (double or wide int) THROUGH the proportional
      scale -- do NOT truncate to an 8-bit-domain int64 first (that would re-introduce the artefact). The
      detector takes the PRE-COMPUTED scene_change_threshold in native units (it does NOT apply any depth
      shift itself), so this lives entirely in the new derivation helper. The layout-proposal high-bit-
      depth derivation check must show the proportional (NOT <<(depth-8)) result.
      ---------------------------------------------------------------------------------------------
      CODER NOTE -- WHAT WE ARE DOING AND WHY (so you can carry the intent, not just the formula):
      We are deliberately NOT reproducing vsCnr2's threshold depth scaling bit-exact. We are using the
      MOST-ACCURATE proportional round-to-nearest method instead, FOR CONSISTENCY WITH THE P.2A
      PARAMETER-SCALING DECISION already in CNR3. The project's settled stance (your handover pack's
      "deliberate divergences" list + the governing rule) is: CNR3 is a FAITHFUL CORRECT redevelopment
      of vsCnr2, not a byte-identical clone. Where vsCnr2's integer arithmetic is DEFINITIONAL (the blend
      >>shift2, the strength/2 curve, the +2>>2 luma average) we reproduce it BIT-EXACT. Where vsCnr2 is
      ACCIDENTALLY LOSSY -- an integer-factor that is exact at the depths the original author tested but
      coarse at others -- we UPGRADE to the proportional round-to-nearest method. P.2A already did this
      for the peak/255 parameter scaling. The threshold's <<(depth-8) is the SAME accidentally-lossy
      integer-factor family (in fact slightly worse: it is exact ONLY at 8-bit, diverging even at 16-bit,
      x256 vs the proportional x257), so the same upgrade applies for the same reason. Net effect: at
      8-bit (the only currently-proven depth) the result is IDENTICAL to vsCnr2 -- nothing you prove now
      changes -- and at 10/12/14/16-bit CNR3's scene-detection sensitivity is proportionally correct
      rather than power-of-two-coarse. Treat this as a RECORDED deliberate divergence (add it to the
      divergences list next to the P.2A entry); do NOT "fix" it back toward vsCnr2 and do NOT flag it as
      a bug. If anything about this classification looks wrong against the source, RAISE IT (charter
      CMS-GAP / rule-deviation) rather than silently reconcile.
      ---------------------------------------------------------------------------------------------
      Rationale for choosing this over the coder's proposed width*height*4*20: (1) exposes the
      familiar scdthr knob rather than baking a fixed sensitivity; (2) reproduces real CNR2
      scene-detection decisions (the point of a CNR2 replacement); (3) max_pixel_diff correctly
      rescales for luma-only vs scene_chroma and for bit-depth/subsampling, which the proxy did
      not. (This SUBSUMES coder tightening #1 -- generalised, depth/subsampling-aware -- using the
      real formula.)
    - DEFAULT scdthr = 10.0 (RESOLVED -- read directly from vsCnr2.cpp: Create_vsCnr2 uses
      args[2].AsFloat(10.0); scdthr is constrained to [0.0, 100.0]). This is the CNR2 default and is
      the P.11C live default. scdthr is a double in vsCnr2; CNR3 may carry it as the pre-computed
      int64 diff_max plus the source double, designer to confirm the carried representation.
      For PROOF harnesses, still use CONSTRUCTED clips + EXPLICIT thresholds that force cut/no-cut
      deterministically (proofs do NOT depend on the live default).

S2. ENABLE DETECTION AT THE LIVE RECURSIVE COMPUTE SITES.
    - Use cnr3_process_caller_supplied_vapoursynth_frame_triplet_with_scene_change
      (passing the Cnr3SceneChangeConfig) at the sites that HAVE a valid previous
      filtered output:
          branch-c: predecessor-present TARGET compute;
          branch-d: recovery HOLE compute;
          branch-d: recovery TARGET compute.
    - Do NOT force the scene-change variant into fresh-start/floor (category 2/3): they
      have no predecessor. Keep the two public entry points distinct (do not collapse).
    - Reset is FREE: once the scene-change variant runs, the existing reset (chroma-copy
      on cut) is exercised live. No new pixel reset algorithm. P.11C PROVES it runs live.

S3. THREAD scene_change_detected INTO EVERY COMPUTED-OUTPUT STORE THAT CAN PRODUCE A CUT.
    (This is the coder's key correction -- it is BROADER than the final-target wrapper.)
    Sites:
          branch-c final TARGET store;
          branch-d per-HOLE stores;
          branch-d final TARGET store.
    Decision (centralised, not scattered):
          store_as_checkpoint = grid_checkpoint || scene_change_detected
    via ONE helper, e.g. cnr3_live_output_frame_should_store_as_checkpoint(...), so the
    "grid || scene" logic is not duplicated across branches.
    Threading shape: prefer a small store-request struct or named boolean over another
    anonymous bool param, e.g.
          struct Cnr3LiveOutputStoreRequest { int frame_number; bool force_checkpoint; };
    The request-struct approach is cleaner if the store wrapper is already gaining semantic
    weight. RATIFY the exact public shape IN the source-confirmed layout proposal (STEP 1),
    before any patch.

S4. CHECKPOINT STORE/PROMOTION -- ATOMIC, PROMOTE-ONLY (CMS 6.6).
    - The checkpoint flag/promotion decision MUST enter the AS2 store atomic. It must
      NOT be a later separate promotion under a second lock.
    - Primitive by site:
          isolated final-target store (no pin)  -> store_checkpoint_owned_frame(...)
            (its promote path raises an existing non-checkpoint slot to checkpoint);
          recovery stores that ALSO pin         -> the combined store-and-pin path with
            is_checkpoint, e.g. store_owned_frame_and_record_pin(..., is_checkpoint, ...)
            or the planned-hole variant store_recovery_plan_hole_owned_frame_and_record_pin
            (..., is_checkpoint, ...). Flag-set AND pin-record under the SAME atomic.
    - The exact primitive name is not the requirement; the ATOMIC + PROMOTE-ONLY property
      is. Confirm the exact call shapes against the latest source (item 0).

S5. PER-HOLE CHECKPOINTING IN RECOVERY (branch-d).
    - CMS 9.2: if a cut is detected at hole K, output[K] is reset/fresh-started, stored
      WITH the checkpoint flag, and the ascending walk continues. So each hole's store
      must take that hole's own scene_change_detected bit and checkpoint/promote that hole
      atomically -- NOT only the final target.
    - Detection against a reconstructed predecessor (floor output or prior hole output) is
      CORRECT: the reconstructed predecessor IS the previous filtered output for the
      ascending walk; it need not be cache-resident before compute.

S6. KDT PROOF FIELDS.
    Per-frame (live): p11c_called, scene_change_deferred, scene_change_detection_used,
      scene_chroma_used, scene_change_threshold, scene_change_diff_total,
      scene_change_samples_examined, scene_change_detected, scene_change_reset_output_used,
      recursive_chroma_blend_used, store_as_checkpoint, scene_checkpoint_store,
      checkpoint_promoted, resulting_slot_is_checkpoint.
    Per-hole (recovery): hole=K, hole_scene_change_detected, hole_scene_change_reset_output_used,
      hole_store_as_checkpoint, hole_resulting_slot_is_checkpoint (or equivalent compact lines).
    On ENABLED recursive branches (branch-c target, branch-d hole/target), flip:
          p11c_called=1, scene_change_deferred=0, scene_change_detection_used=1.
    On FRESH-START / FLOOR paths (category 2/3 -- frame 0, bounded-search floor), do NOT emit
      scene_change_deferred=1 after this scope. "Deferred" implies unfinished work; these paths
      are NOT-APPLICABLE (no previous filtered output to detect against -- the CMS-settled
      boundary). Emit instead:
          scene_change_detection_used=0, scene_change_deferred=0, scene_change_not_applicable=1
      (optionally scene_change_not_applicable_reason=no_previous_filtered_output). This matters
      for later diagnostics and for human reading during first real-footage tests.
      (This is coder tightening #2.)

4. fmParallel INTERLEAVING (carry in the design note; no stress validation in P.11C)
--------------------------------------------------------------------------------
    - checkpoint flag raise-only, never demote;
    - duplicate checkpoint store promotes an existing non-checkpoint slot (data unchanged);
    - duplicate non-checkpoint store cannot demote an existing checkpoint;
    - pin count and checkpoint flag coexist under cache lock;
    - recovery store-and-pin and checkpoint promotion under ONE atomic;
    - no after-the-fact second-lock promotion.
Benign interleavings to cite: (A stores K non-cp; B detects K cut -> promotes),
(A stores K cp; B computes K non-cp -> no demote), (A pins/adopts K while B promotes K
-> pin+flag coexist under the cache lock). Actual fmParallel STRESS validation is deferred.
