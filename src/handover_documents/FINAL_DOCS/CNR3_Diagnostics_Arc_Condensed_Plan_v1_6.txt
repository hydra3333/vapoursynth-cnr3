Goal: implement the 14-family D-SUM observe-only telemetry framework
(cnr3_diagnostics_specification_v1_5.md + cnr3_memory_diagnostics_spec_v2.md) in
as FEW phases as the work honestly allows, NOT one phase per D-SUM family.

WHY THIS CONDENSES (the key insight):
The 14 D-SUM families are not 14 design problems -- they are 14 instances of ONE
pattern already fully specified in spec §2.3:
  - a compute gate (CNR3_DIAG_COMPUTE_DSUMxx) and a print gate (CNR3_DIAG_PRINT_DSUMxx);
  - stderr-only emission, OUTSIDE all locked/atomic scopes (§2.1, §2.2);
  - observe-only: a compute-disabled build must be behaviourally identical (§2.3.1,
    R-PROCESS-19).
The per-family variation is WHICH fields and WHICH observation points -- mechanical
once the pattern is proven once. So we prove the pattern + harness ONCE, then roll
out the families in a few subsystem BATCHES, not one-by-one.

--------------------------------------------------------------------------------
THE CONDENSED PHASE SET (target: ~4 phases, each a single commit)
--------------------------------------------------------------------------------

DIAG.1 -- FRAMEWORK + ONE REFERENCE FAMILY + OBSERVE-ONLY PROOF
  - FIRST, verify against source: read build_config.h (and any existing diagnostics
    headers) and REUSE the existing compile-gate convention. build_config.h already
    hosts CNR3_SCAFFOLD_TINYCACHE_FOR_DIAGS_ONLY and the project already has the
    CNR3_KEYSTONE_DEV_TRACE dev-trace gate + [KDT]/[KDT-SUMMARY] emission — the D-SUM
    gates and summary writer should EXTEND these conventions (same header home, same
    stderr-only discipline), NOT introduce a parallel mechanism. Report what already
    exists before adding anything (R-PROCESS-21: do not silently restructure proven
    scaffold; propose additions).
  - Flesh out the diag translation units (cnr3_diagnostics.{h,cpp},
    cnr3_cache_diagnostics.{h,cpp}) from the shells: the gate macros, the
    stderr line writer (already partly present), the summary-formatting helpers.
  - Implement ONE representative family end-to-end as the reference: D-SUM-01
    (frame request arrival / ordering) -- simple, getFrame-level, no lock subtlety.
  - Prove the load-bearing INVARIANT for the whole arc ONCE: the compute-disabled
    observe-only proof (§2.3.1 / R-PROCESS-19) -- a build with CNR3_DIAG_COMPUTE_*
    off is behaviourally identical (selftests + a .vpy byte-for-byte match).
  - Deliverable: framework + D-SUM-01 + the observe-only proof. This phase carries
    the only genuinely NEW risk (gate discipline, lock-scope, macro-off equivalence);
    once proven here it is inherited by all later families.

DIAG.2 -- CACHE-CORE FAMILY BATCH
  - Implement the families that observe cache-core state, as ONE batch (they share
    the cache_diagnostics TU, the same outside-lock emission discipline, and the
    selftest surface): D-SUM-04 (ownership/pin/lookup-ref balance), D-SUM-05 (cache
    integrity/teardown), D-SUM-08 (store/duplicate/first-in-best-dressed), D-SUM-10
    (prune/eviction safety), D-SUM-11 (hot-zone operation).
  - Proof: extend the existing cache-core selftests to assert each family's counters
    where they already have deterministic scenarios (the D-series + prune tests
    already exercise these paths) + re-run the observe-only macro-off check.
  - CHURN-FIELD PRIORITY (coordinator interest — inherent-vs-tunable recovery churn):
    within this batch, D-SUM-10 (prune) and D-SUM-11 (hot-zone) must include the
    RE-CHURN fields specifically -- count "evicted-then-later-re-requested" (prune) and
    "hot-zone-evicted-then-re-requested-into" (hot-zone). Those are the avoidable-churn
    signals; a plain evict count does not distinguish inherent from tunable. Field-map
    choice only; no phase/sequencing change.

DIAG.3 -- GETFRAME / RECOVERY / RETURN FAMILY BATCH  (split into 3a / 3b / 3c)
  The families that observe the live getFrame dispatch + recovery. Originally scoped as
  one batch of seven; SPLIT during execution into three sub-batches by domain + risk
  gradient (observe-only summaries first, the invasive bail-touching family last):

  DIAG.3a -- RECOVERY / RECOMPUTE / CHURN TRIO  [COMMITTED 2026-07-04]
    D-SUM-03 (recovery-search), D-SUM-12 (recovery planning/hole-filling + RECOVERY-RATE),
    D-SUM-13 (recalculation). These three answer the CHURN question (below). Proven:
    all-on four-way 56/56; R-PROCESS-19 five-config matrix; S-series -r 1 with
    recovery_plan_balance==0 under churn (S8: 171 plans created+destroyed), saturation
    false. Recovery-rate baseline captured: S1 0% / S3 27.5% / S7 0.375% / S8 21.4% --
    the S8-vs-S7 contrast shows recovery churn is driven by ARRIVAL DISORDER within a
    working set (shuffle), not by distant seeking (jumps).

  DIAG.3b -- LIFECYCLE / RETURN / SCENE-RESET BATCH  [NEXT]
    D-SUM-06 (source request/retrieve/release), D-SUM-07 (temp-output/owned-output-ref
    lifecycle), D-SUM-09 (return-decision/transfer), D-SUM-14 (scene-change/reset/
    checkpoint-promotion). Observe-only summaries + lifecycle balances (the D-SUM-06/07/09
    balances are the getFrame-side analogue of the DIAG.2b cache-side balances). D-SUM-14
    composes directly with the P.11C work.

  DIAG.3c -- PLAN / RESULT PLAN-TRACE FAMILY  [AFTER 3b; SPEC-v2 FIRST]
    The per-output-frame plan-vs-result trace: for each requested frame, an O-record (the
    PLAN arInitial built -- strategy + target/predecessor/anchor/floor/holes/sources/
    pinned) and an R-record (the RESULT arAllFramesReady produced -- computed/adopted/
    unpinned/failed-where), emitted as clean copy-pasteable sorted blocks (by-datetime,
    by-frame, by-phase), buffered in a preallocated windowed buffer, flush-always, dumped
    on clean-end OR failure-bail. Spec drafted: CNR3_DIAG_PlanResult_Vocabulary_and_
    Architecture_Spec_v1.md (five enum sets, *=checkpoint glyph, ~13 failure-reason
    categories). Coder cross-check DONE (DIAG.3a cycle); its findings -> a SPEC v2 BEFORE
    scoping 3c: (i) `sources` role must be branch-specific (cache_hit/frame0/pred_present
    request n WITHOUT populating source_request_frame_numbers); (ii) a source-line site-to-
    failure-category TABLE, not a message parser; (iii) add ALLOCATION_FAILED /
    RECOVERY_PLAN_FAILED_OR_REFUSED / HOT_ZONE_OBSERVATION_FAILED to the categories (bail
    sites are >50 once arInitial + top-level are counted, not ~50); (iv) compile-time
    from/to for the first cut (DECIDED); (v) dump-on-bail is the INVASIVE part.
    WHY LAST: 3c is the only DIAG family that touches the ~50+ setFilterError BAIL SITES
    (control-flow-adjacent -> R-PROCESS-21), the most invasive diagnostic in the arc. It
    lands after the getFrame path is fully instrumented + understood, with its own focused
    review. LIKELY SUB-SPLIT when scoped: 3c.1 = buffered plan/result capture (observe-
    only, NO bail touch); 3c.2 = the dump-on-bail mechanism (the invasive part, its own
    R-PROCESS-21 sub-review). Decide the split at 3c scoping, not now.

  ------ CHURN-FIELD PRIORITY (coordinator interest) -- SATISFIED in 3a ------
  D-SUM-12 includes the RECOVERY-RATE fields (total frames, frames-present cache-hit,
  frames-recovered EXACT vs FLOOR, recovery-as-%, mean/max span) -- THE counter answering
  "is the ~50% fmUnordered-no--r-1 recovery inherent or tunable" (the FI-10/FI-11 multi-
  thread sub-finding). The -r 1 S-series gave the DETERMINISTIC baseline (above); the
  real-threads comparison (num_threads>1, higher -r) is the LATER step isolating
  concurrency-specific churn.

  ------ FI-11: RING <-> RECOVERY CORRELATION (do NOT lose -- coordinator intuits it WILL be needed) ------
  D-SUM-10's recently-evicted RING (committed in DIAG.2a) records WHAT was evicted;
  D-SUM-12 (DIAG.3a) records WHAT was rebuilt via recovery. The FI-11 question -- how much
  of the recovery churn is evict-then-REBUILD of a region we just evicted -- is answered
  by CORRELATING the two.
    * OFFLINE correlation: AVAILABLE NOW, no code. Read the [DSUM10-RING-*] dumps against
      D-SUM-12's recovered targets from the SAME run and ask "were the recovered frames in
      the evicted region." USE PLANNED: during the FI-11 inherent-vs-tunable analysis,
      naturally post-arc / before the real-footage campaign. First data point already
      exists (S8 21.4% shuffle-driven vs S7 0.375% jump-driven).
    * IN-RUN correlation COUNTER (a live field flagging "recovered target was in the
      recently-evicted ring"): DEFERRED (FI-11). Needs a getFrame-side read of cache-
      internal ring state -> breaks the getFrame/cache boundary + couples DSUM10+DSUM12
      gates. UNSCHEDULED / CONDITIONAL: build ONLY if the offline correlation proves
      insufficient OR the signal is wanted LIVE (e.g. watching churn during the real-
      footage campaign). If it lands: a small DSUM10+DSUM12-gated follow-up, investigate-
      first, observe-only, the cross-family read scoped carefully. COORDINATOR NOTE: this
      is intuited to be needed eventually -- keep it visible, do not let it decay to a
      forgotten FI line.

DIAG.4 -- MEMORY DIAGNOSTICS + ARC CLOSE
  - D-SUM-02 (memory diagnostics) per cnr3_memory_diagnostics_spec_v2.md (snapshot
    tables, delta columns, the frame-interval constant).
  - Final whole-framework observe-only proof (all compute gates off => identical),
    summary-readability pass, and arc close-out in the ledger.

--------------------------------------------------------------------------------
WHY NOT FEWER (the honest floor)
--------------------------------------------------------------------------------
Could compress to 2-3, but the natural seams are real: DIAG.1 isolates the only new
RISK (the framework + observe-only invariant) so it is proven before any rollout;
DIAG.2/.3 split by TRANSLATION UNIT + proof-harness (cache-core selftests vs live
.vpy), which is where the work and the review naturally divide; DIAG.4 is the memory
spec (a separate document with its own table format) + close. Collapsing .2 and .3
would mix two proof surfaces in one review. Four single-commit phases is the
condensed floor that keeps each commit independently reviewable and each proof clean.

--------------------------------------------------------------------------------
WHAT KEEPS IT CONDENSED (process notes)
--------------------------------------------------------------------------------
- ONE design pass up front (this plan + a short per-batch field map), NOT a
  per-family design cycle. The spec already IS the design.
- Families within a batch share one patch + one proof run -- reviewed together.
- No new behavioural code anywhere (observe-only); the review bar per family is
  "fields correct + gated + outside locks", not algorithm correctness.
- The observe-only macro-off proof is the single recurring gate; proven in DIAG.1,
  re-checked (cheaply) per batch.

--------------------------------------------------------------------------------
SEQUENCING NOTE
--------------------------------------------------------------------------------
Per the CURRENT ledger (DELTA v4.23) the order is: live cache-pressure wiring arc W.1->W.2->W.3 (COMPLETE) ->
marshalling-optimisation arc (COMPLETE, ~-80%) -> DIAGNOSTICS arc (THIS plan, ACTIVE) -> first real-footage
validation / 576p50 campaign -> fmParallel. Diagnostics is sequenced BEFORE real-footage deliberately: the W.3 eviction-proof harness proves
the live cache evicts SAFELY but is blind to eviction-POLICY health (over-prune / thrash / hot-zone efficacy /
recovery churn), so the footage campaign runs instrumented. This plan is for the diagnostics slot. Diagnostics could
also run PARTLY before real-footage (D-SUM-01/03/14 would aid first-footage
debugging), but the spec is observe-only so it does not block footage either way.
Decision on exact placement (before vs after first real footage) is the coordinator's.
