## Main review finding

The patch is probably small, but the **proof wording is the dangerous part**.

The new counter is not “within back radius” and not “frame-local”; it is **eviction-recency bounded**. The document is clear on that distinction: frame-number locality is rejected as the discriminator, and `eviction_gap` is the meaningful value. 

So I would insist the implementation, emission label, proof notes, and commit message all use:

```text
frames_recently_evicted_then_re_requested
```

not any `within_back_radius`, `local`, `near_frame`, or `back_radius` wording.

## Questions I would send to the designer

### Q1 — Is the `eviction_gap == 0U -> 1U` normalization intended to affect the new counter?

The scope says to hoist the existing computation including the `==0 -> 1` normalization, then gate the counter on that value. 

That means an immediately re-requested newest eviction counts as gap `1`, not `0`.

I think that is correct because it preserves existing histogram semantics, but I would ask the designer to confirm:

```text
Confirm: the recency counter uses the normalized eviction_gap, where raw gap 0 is treated as 1, exactly like the existing histogram.
```

### Q2 — What is the numeric acceptance bound for S9/S9b?

The proof matrix says S9/S9b should be “SMALL / near 0” and much less than old 481/565. 

That is directionally clear but not numerically crisp. I would ask:

```text
For S9/S9b, is acceptance simply “much less than old 481/565 and plausibly explained by gap <= Z”, or do you want a hard ceiling?
```

I would avoid inventing a hard limit. The safest proof wording is probably:

```text
S9/S9b: sharply reduced from old raw counter; any remaining value must be explainable by near eviction_gap bins and remain <= old-style total.
```

### Q3 — Do we need to print or separately record the chosen S9e tuning?

The S9e candidate is intentionally adjustable if it does not produce a small enough eviction gap. 

I would ask:

```text
If the proposed S9e [0, 5], segment_length=120 does not produce >0, may the coder tune only the second jump target/segment shape and record the final chosen values in the proof notes?
```

The scope already allows this, but it is worth making explicit before patching the `.vpy`.

### Q4 — Does the proof need the exact gap histogram cross-check, or only a plausibility cross-check?

The document says the new counter should be roughly bracketed by gap histogram near bins. 

But `Z = BACK_RADIUS + 2`, so under TINY-100 `Z = 17`; that is not exactly one printed histogram bin. It spans all `1-10` plus part of `11-50`. Under NORMAL it may span all `1-10`, all `11-50`, plus part of `51-100`.

So I would ask:

```text
Confirm the histogram check is qualitative/plausibility only, not a byte-exact equality, because the printed bins are coarser than Z.
```

### Q5 — Should plantrace/all-families be proof-only, not final committed gate state?

The proof matrix says run under TINY-100, all families plus plantrace on, `-r 1`. 

I would ask:

```text
Confirm plantrace/all-families-on is proof configuration only; final committed gate state should return to the project’s normal build_config baseline unless explicitly directed otherwise.
```

This avoids repeating the DIAG.4 confusion.
