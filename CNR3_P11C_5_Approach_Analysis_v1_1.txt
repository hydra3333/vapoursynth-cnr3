CNR3 P.11C.5 -- SCENE-CUT CHECKPOINT FOUND AS RECOVERY ANCHOR -- APPROACH ANALYSIS
================================================================================
Designer pre-scope analysis, verified against post-.4 source. The FINALE of the
P.11C arc: the end-to-end checkpoint EFFECT that .3 and .4 honestly deferred with
resulting_slot_is_checkpoint_expected. Next: coder read, then scope, then proof.

Baseline: committed through CMS07-P.11C.4-branch-d-recovery-scene-detection-enable.
Branch-c (.3) and branch-d (.4) scene detection PROVEN. P.11C.5 closes the loop.

--------------------------------------------------------------------------------
1. WHAT P.11C.5 PROVES
--------------------------------------------------------------------------------
That a checkpoint CREATED BY A SCENE CUT (P.11C.3/.4) actually does its job: it
SURVIVES prune when ordinary outputs around it are evicted, and a LATER recovery
search descending into that now-cold region FINDS it as the exact-anchor start point.
This is the "the checkpoint did its job" link -- from "we marked it a checkpoint"
(.3/.4 expected) to "the checkpoint was used as a real recovery anchor" (observed).

--------------------------------------------------------------------------------
2. KEY FINDING -- P.11C.5 IS A COMPOSITION OF ALREADY-PROVEN MECHANISMS
--------------------------------------------------------------------------------
Two source facts (verified post-.4):

(a) is_checkpoint IS A SINGLE BOOL WITH NO PROVENANCE. A scene-cut checkpoint and a
    grid checkpoint are BYTE-IDENTICAL on the cache slot (Cnr3CacheSlot::is_checkpoint).
    The recovery search neither knows nor cares HOW a checkpoint was created.

(b) THE RECOVERY SEARCH SELECTS FIRST-PRESENT DESCENDING, REGARDLESS OF CHECKPOINT
    FLAG. Checkpoints are NOT preferred; they simply SURVIVE eviction (non-checkpoint
    pool prunes; checkpoint pool retained, MIN_RETAIN..MAX_RETAIN, frame 0 never pruned).
    In a cold (seeked-into) region the surviving present frames ARE the checkpoints, so
    the search finds them because they survived, not because it seeks them.

Therefore the "scene-cut checkpoint found as anchor" behaviour is the COMPOSITION of:
  - P.11C.4 (PROVEN): a scene cut creates a checkpoint (is_checkpoint=1) live.
  - CHECKPOINT-CLASS RETENTION (proven in the cache-core prune phases): prune evicts
    UNPINNED NON-CHECKPOINT frames (see remove_unpinned_noncheckpoint_frames_bounded);
    checkpoints are a SEPARATE retention class (retain_checkpoint_count, checkpoint_
    candidate_order) and are NOT prune-eligible by class -- INDEPENDENT of pin status.
  - D.1 / D.2 (PROVEN): exact-anchor recovery descends and anchors on the nearest present
    cached output, provenance-blind (the D3 harness has a d2regress exact-anchor mode).

*** CORRECTION (coder-caught): do NOT lean on D.5 for the survival step. D.5 proves a
PINNED checkpoint survives prune (pin + checkpoint composition). P.11C.5 must prove the
STRONGER live case: an UNPINNED, scene-cut-created checkpoint survives ordinary prune
pressure BECAUSE IT IS IN THE CHECKPOINT-RETENTION CLASS, while its unpinned NON-checkpoint
neighbours are evicted. Verified in source: eviction targets unpinned non-checkpoints
(remove_unpinned_noncheckpoint_frames_bounded); checkpoint retention is a separate class,
not a pin effect. If C survived only because it was still pinned/hot, the proof is WEAKER
than intended -- the .vpy must avoid that accidental shape. ***

Because the code path is provenance-blind, there is NO NEW UNIT-LEVEL CODE PATH to prove.
P.11C.5 is an END-TO-END / INTEGRATION proof that the composition behaves as intended --
NOT a new mechanism.

--------------------------------------------------------------------------------
3. LIKELY SCOPE -- PROOF-ONLY (no source change expected)
--------------------------------------------------------------------------------
Expectation: P.11C.5 needs NO source change. The .3/.4 patches already create scene-cut
checkpoints; the cache-core already survives prune and anchors on present checkpoints.
P.11C.5 = a .vpy scenario that:
  (i)   creates a SCENE CUT at a frame C that is *** NON-GRID *** (C is NOT a multiple of
        CHECKPOINT_INTERVAL) -- so C becomes a checkpoint ONLY because the scene cut promoted
        it, not because of the grid rule. (Critical: if C were a grid frame, a reviewer could
        say it survived via grid checkpointing, not the scene cut.) Assert at creation:
        N=C scene_change_detected=1 store_as_checkpoint=1 resulting_slot_is_checkpoint(_expected)=1.
  (ii)  drives enough OTHER frames that the bounded NON-checkpoint pool evicts C's ordinary
        neighbours, while C -- being in the checkpoint-retention class and UNPINNED by then --
        survives. (Not because C is pinned/hot: it must be unpinned and out of any hot zone.)
  (iii) issues a LATER COLD request for a frame N > C whose nearer predecessors C+1..N-1 are
        absent, so the bounded descending search reaches C and anchors on it.
  (iv)  asserts via KDT the GOOD proof shape (below).

GOOD vs BAD proof shape (coder-flagged):
  BAD:  C survived because it was still pinned / hot / never under prune pressure.
  GOOD: C survived AFTER its ordinary neighbours were evicted, BECAUSE C was a checkpoint
        (unpinned, checkpoint-class), and later recovery found C as the nearest present anchor.
MINIMUM KDT CONTRACT for P.11C.5:
  At creation (frame C):  N=C scene_change_detected=1 store_as_checkpoint=1
     resulting_slot_is_checkpoint=1 (branch-d hole) or _expected=1 (branch-c/target), and C non-grid.
  At later recovery:      branch=RECOVER recover_branch=exact-anchor anchor=C
     (ideally anchor_is_checkpoint=1), with holes / source_requests showing C+1..N-1 were absent
     (proving C was the nearest present output).
OBSERVABILITY = the likely source-change boundary: if the recovery KDT does NOT already print
anchor=<frame>, that is a BLOCKER for the .vpy proof and a small KDT-only field is required. If
anchor= is printed but anchor_is_checkpoint= is not, the proof is still acceptable when the
creation KDT proves C was stored as a checkpoint AND C is non-grid -- but adding
anchor_is_checkpoint=1 makes it much cleaner. Any such addition is KDT-ONLY (no behaviour change).

--------------------------------------------------------------------------------
4. THE HARNESS CHALLENGE (the real work of .5)
--------------------------------------------------------------------------------
The difficulty is constructing a .vpy that deterministically:
  - creates a scene-cut checkpoint at a known frame C, AND
  - evicts C's ordinary neighbours but RETAINS C, AND
  - forces a later bounded recovery that descends to C.
This needs enough frames to exercise the prune (the bounded pools have real capacities --
non-checkpoint pool ~110 with overflow, checkpoint pool max 16 / min 6 retained), which is
a MUCH larger synthetic clip than the 4-frame D-harnesses. Two sub-questions for the coder:
  Q1. What is the minimum frame count / request pattern that reliably (a) creates a scene-cut
      checkpoint, (b) prunes its non-checkpoint neighbours, (c) leaves it as the first-present
      anchor for a later cold request? (Depends on the live pool capacities + CHECKPOINT_INTERVAL.)
  Q2. Does the recovery KDT already print the anchor frame number AND a flag/means to confirm
      the anchor slot is a checkpoint (so the proof can assert "anchored on the scene-cut C")?
      If not, a small KDT-only field may be the single source change.

--------------------------------------------------------------------------------
5. ALTERNATIVE / FALLBACK FRAMING (if a full prune-driven .vpy is impractical)
--------------------------------------------------------------------------------
If deterministically driving the live prune from a .vpy proves too fragile (the pools are
sized for realistic workloads, so forcing eviction may need hundreds of frames and precise
request ordering), an acceptable alternative is a CACHE-CORE SELFTEST that composes the
proven primitives directly: store a scene-flagged checkpoint, store+prune enough non-
checkpoint neighbours, then run the bounded search and assert it anchors on the scene
checkpoint. This is the same composition, proven at the unit level where eviction is
deterministic. Designer leans: TRY the .vpy first (true end-to-end). If live prune-driving is too fragile,
fall back to a cache-core composition selftest -- but FRAME IT CORRECTLY: the selftest proves
deterministic cache survival (unpinned checkpoint retained while non-checkpoint neighbours
evicted) + anchor selection for a frame marked checkpoint by the SAME store-request route;
P.11C.4 REMAINS the live proof that scene detection feeds that route. The selftest cannot, by
itself, prove the live scene-cut created C -- it proves the cache half; .4 proves the scene half.
Coder to advise which is more reliable given the live pool sizes.

--------------------------------------------------------------------------------
6. DESIGNER READ
--------------------------------------------------------------------------------
P.11C.5 is the arc's capstone but is mechanically the LIGHTEST subphase: it proves a
COMPOSITION of already-proven, provenance-blind mechanisms, almost certainly with no
behavioural source change (at most a small KDT observability field). The real work is a
harness that drives the live prune deterministically -- larger than the D-harnesses -- with
a selftest-composition fallback if the .vpy prune-driving is too fragile. No new atomic, no
new pixel maths, no new checkpoint mechanism.

--------------------------------------------------------------------------------

--------------------------------------------------------------------------------

    modulo any KDT observability field.
Q5. Confirm C can be chosen NON-GRID relative to CHECKPOINT_INTERVAL (so C is a checkpoint
    solely via the scene cut, not the grid rule).
Q6. Confirm the recovery KDT can prove anchor=C, and preferably anchor_is_checkpoint=1 (if not
