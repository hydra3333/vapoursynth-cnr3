CNR3 - PIXEL-LAYER BRIEFING FOR THE CODER
Bit depth, colour spaces, the luma calculation, and staying aligned with CNR2

Purpose of this note
--------------------
P.1A and P.2A built the response-table layer (the lookup helper, the weight-table
builder, and the per-plane configuration surface). The next phases are the pixel
maths: P.3A weighted blend, P.4A downsampled luma, P.5A frame-processing core,
P.6A scene change. Those phases must compute correctly at all supported bit depths
and across the agreed colour spaces, and must stay bit-exact with the CNR2 source
they are derived from. This note explains the facts that govern that, and then lists
exactly what to watch for. Hopefully none of this changes P.2A; it is the context
for P.3A+.

At P.3A, the CNR2/vscnr2 source will be supplied so the blend can be verified
line-by-line against it. Treat CNR2 as the pixel-maths reference of record. Do NOT
adopt CNR2's predecessor/recovery behaviour (see the last section).


PART 1 - THE FACTS (what CNR2 actually does)

1. Accepted formats (fixed; do not widen without an explicit design decision)
   - Integer YUV only. No float. No RGB.
   - Planar subsampling: 4:2:0, 4:2:2, 4:4:0, 4:4:4 only. CNR2 restricts to
     subSamplingW <= 1 and subSamplingH <= 1.
   - Exactly three planes. Grey / 4:0:0 is NOT supported and is not in scope.
   - Native bit depth, 8..16-bit, treated as a RANGE: 8, 10, 12, 14, 16 are all in
     scope. It is not an enumerated whitelist of a few depths. CNR2 is templated on
     T = uint8_t or uint16_t and works for any depth in the range.

2. Bit-depth handling - compute in native depth, widen the ACCUMULATOR (this is the
   key point, and it is the answer to "what about unsigned/overflow at high depth")
   - Pixels are read and written at their native bit depth. CNR2 does NOT promote or
     demote pixels to some intermediate working depth.
   - Overflow is handled by widening only the arithmetic accumulator. The per-sample
     chroma blend is:

         dst = (weight * prev + (shift - weight) * cur + shift1) >> shift2

     where:
         weight  is int64_t        (it is the PRODUCT of two response-table entries,
                                    so it can be large - this is why it must be 64-bit)
         shift2  = depth << 1       (i.e. 2 * depth; 32 for 16-bit)
         shift   = 1LL << shift2     (full-weight normaliser)
         shift1  = the rounding addend (rounds the >> back into pixel range)
         prev    = previous FILTERED output chroma (output[N-1]), not source[N-1]
         cur     = current source chroma (source[N])

   - That int64 accumulator together with shift2 = depth<<1 IS the historical
     "Fixed high bit depth chroma overflow" fix: at high depth, weight * pixel
     overflows 32-bit, so the accumulator was widened to 64-bit and the shift scaled
     by depth. Reproduce this exactly. Do not "simplify" it back to 32-bit maths.

3. The 8-bit -> native parameter scaling (already implemented in P.2A, stated here so
   the blend uses the scaled values consistently)
   - Public threshold/strength parameters are on the historical 8-bit Cnr2 scale.
     Internally they are scaled to the native peak by:

         scaled = (int64(clamp(value_8bit, 0, 255)) * sample_peak + 127) / 255
         sample_peak = (1 << bits_per_sample) - 1

     This is round-to-nearest, done with an int64 multiply to avoid 32-bit overflow.
     P.2A implements this exactly. The blend must consume the scaled (native-domain)
     threshold/strength, never the raw 8-bit values.

4. The luma calculation - downSampleLuma (the "fancy" luma bit)
   - Luma Y is copied to output UNCHANGED. CNR3 does not filter luma.
   - Luma is used only as an INPUT to the chroma blend decision. downSampleLuma is a
     2x2 box average of luma onto the chroma grid (shifted by subSamplingW/H), so the
     luma difference can be measured at chroma sampling positions.
   - The chroma blend weight depends on BOTH the luma difference and the chroma
     difference:

         weight = response_y(diff_downsampled_luma) * response_chroma(diff_chroma)

     So the "Y response table" is the luma-DIFFERENCE response that feeds the CHROMA
     blend. It is not a luma filter. Never use it to modify output luma.
   - In 4:4:4 and 4:4:0 (subSamplingW == 0 and/or subSamplingH == 0) the 2x2 average
     degenerates - e.g. with subSamplingH == 0 the second row equals the first, so the
     four-tap average becomes 2*row0[x0] + 2*row0[x1]. CNR2 does this deliberately.
     Match CNR2's degenerate behaviour; do not "correct" it to something else.

5. Response tables and per-plane decomposition (P.1A/P.2A, consistent with CNR2)
   - mode is a 3-char string: mode[0] -> Y curve, mode[1] -> U curve, mode[2] -> V
     curve. 'x' = narrow, 'o' = wide. Default "oxx" = Y wide, U narrow, V narrow.
     'x' does NOT mean off and 'o' does NOT mean on - all three planes get a table.
   - Each plane's table is built from (threshold, strength) plus the curve. These map
     to (ln,lm) for Y, (un,um) for U, (vn,vm) for V. This is exactly P.2A's
     Cnr3ResponsePlaneConfig{threshold_8bit, strength_8bit, curve} per plane.
   - The raised-cosine weight uses strength/2 as INTEGER division before the cosine
     (this is why odd strength 255 peaks at 254, not 255). Preserve this at every bit
     depth - it is part of bit-exact compatibility, not a rounding accident.

6. Scene change (relevant at P.6A)
   - diff_total accumulates abs(diff_y << (subSamplingW+subSamplingH)) (plus chroma
     diffs if scenechroma is enabled). If diff_total > diff_max (a threshold scaled by
     scdthr and resolution), the chroma path returns -1 and the frame is returned as
     source unchanged - i.e. on a detected cut, output = source, no recursive blend.
   - Scene detection runs DURING the chroma compute (it accumulates while processing
     and bails at -1), so in CNR3 it is intrinsic to the compute step, not a separate
     pre-pass.


PART 2 - WHAT YOU MUST WATCH FOR (to get full bit depth, the agreed colour spaces,
and CNR2 alignment right)

Bit depth / arithmetic
  - Keep the signed difference SIGNED end to end. signed_diff = current - previous can
    be negative, and it is used to index the response table. There must be NO unsigned
    type anywhere on the path from reading the pixel to indexing the table. An unsigned
    intermediate will wrap a small negative difference into a huge positive value and
    index garbage. Check every cast and every intermediate variable's type.
  - Use an int64_t accumulator for the blend. weight is a product of two table entries
    and overflows 32-bit at high depth.
  - Use shift2 = 2*depth and the same rounding addend (shift1) as CNR2. Verify these
    against the CNR2 source at P.3A; do not guess them.
  - Do not promote/demote pixels to a working depth. Read and write native; widen only
    the accumulator.
  - 16-bit access: when you reinterpret the plane as uint16_t
    (reinterpret_cast<const uint16_t*>), the stride must be a multiple of 2 (it is in
    practice, but assert/confirm it). Get the per-plane, per-depth stride arithmetic
    right - this is a common source of silent corruption at 16-bit.
  - Consume the SCALED (native-domain) threshold/strength from the P.2A scaling helper,
    never the raw 8-bit parameter values.

Colour spaces / subsampling
  - Read subSamplingW and subSamplingH from the format and parameterise ONE compute
    loop across all of 4:2:0, 4:2:2, 4:4:0, 4:4:4. Do not write per-format special
    cases beyond what the subsampling shifts naturally give you.
  - Reject anything outside the accepted set (non-YUV, float, subSamplingW/H > 1, not
    three planes). Fail cleanly; do not attempt to process it.
  - Do NOT resample chroma and do NOT touch chroma siting/location. CNR2 computes in
    native subsampling and never resamples. Just box-average luma to the chroma grid.
  - Handle the 4:4:4 / 4:4:0 degenerate downSampleLuma case exactly as CNR2 does
    (see Part 1, point 4). Watch the right/bottom edge clamping (e.g. x0+1 clamping)
    - off-by-one at the edges is a classic bug here.

Table indexing
  - The signed difference can be as large as +/- sample_peak (e.g. pixel 0 vs pixel
    peak in 16-bit). Confirm the table covers the full range and the lookup is total
    (out-of-range returns 0, never undefined behaviour). The P.1A lookup helper already
    does this; do not bypass it.
  - Use the P.2A table geometry convention: index = signed_diff + sample_peak, table
    size = sample_peak*2 + 1, table_offset = sample_peak. NOTE: the old source used
    table_offset = sample_peak + 1 (size offset*2+1). Those two conventions are
    lookup-equivalent (proven), but if you mix them you get an off-by-one. Use the
    P.2A convention (offset = sample_peak) throughout P.3A+.

Staying aligned with CNR2
  - At P.3A the CNR2 source will be supplied. Verify the blend arithmetic, the shift
    values, the rounding, the signed-difference handling, and the response-curve maths
    line-by-line against it. Prove with exact-integer reference vectors recomputed from
    the CNR2 formula - no tolerance, because bit-exact CNR2 compatibility is the point.
  - The Y (luma-difference) response is combined as a MULTIPLIER into the chroma weight,
    not applied to luma output. Luma is copied unchanged.
  - Use the explicit-previous-output processing boundary
    (process_..._with_explicit_previous_output style), not the CNR2-style
    process_cnr3_frame() predecessor fallback.

The ONE thing from CNR2 you must NOT copy (important)
  - When CNR2 is asked for frame n and the last frame it processed was not n-1, it
    fetches SOURCE[n-1] and uses that as the predecessor - an approximation it gets
    away with only because it is single-threaded and mostly sequential. CNR3 must NOT
    do this. CNR3's whole cache + recovery design exists precisely to provide the
    EXACT output[n-1] (from the cache, or rebuilt via the bounded recovery walk). So:
    take CNR2's pixel maths (blend, response tables, downSampleLuma, scene detect)
    verbatim where proven, but never take its "last_frame != n-1 -> use source[n-1]"
    predecessor/recovery logic. The predecessor always comes from the cache layer.

Process reminder
  - Same delivery discipline as before: propose the phase as text first; for P.3A the
    proposal should come WITH the CNR2 source attached and the reference vectors stated;
    then a downloadable patch reviewed read-first before apply (P.3A touches pixel maths
    that the rest of the pixel arc builds on); then the four-way build/run with actual
    pasted output. Exact-integer equality in all proofs.
