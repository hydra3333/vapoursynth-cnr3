Recommended implementation shape:

```text
1. Observe prune invocation after trigger decision is calculated.
2. Observe prune event if prune_is_required is true.
3. Observe checkpoint prune if checkpoint_prune_is_required is true.
4. After successful detach, record selected/evicted frame numbers into the D-SUM-10 ring.
5. Add frames_evicted and bytes_evicted from detached_count * frame_byte_count.
6. Count checkpoint evictions from candidate_order.is_checkpoint.
7. Mirror/cross-check hot-zone rejected count when available.
```

This is additive and does not need prune-path restructuring.

## One implementation wrinkle

`lookup_frame_and_add_ref(...)` and `lookup_frame_and_add_ref_locked(...)` are currently `const`.

D-SUM-10 wants to mutate diagnostic counters on a lookup miss. That means the patch needs one of these choices:

```text
Option A, recommended:
  make the D-SUM-10 diagnostic stats member mutable under the compute macro.
  This treats diagnostics as logically const, like cache_mutex_ is already mutable.

Option B:
  avoid observing the add-ref lookup path and only observe non-const pin lookup misses.
  I do not recommend this because it risks under-counting re-churn.

Option C:
  make lookup_frame_and_add_ref non-const.
  I do not recommend this because it is broader API/control-flow churn.
```

I recommend **Option A** because it preserves behaviour and avoids changing the proven lookup API. It should be explicitly called out in the patch notes as a diagnostic-only constness accommodation.
