1. WHAT P.11C IS (one paragraph)
--------------------------------------------------------------------------------
P.11C wires scene-change handling into the LIVE getFrame path, uniformly across
branch-a (fresh-start), branch-c (predecessor-present), and branch-d (recovery),
before the first real-footage test. Pixel-level scene-change DETECTION and the
RESET behaviour already exist and were proven in the caller-supplied pixel arc.
The CMS design (cut -> checkpoint promotion) is fully settled (CMS 6.4 / 6.5 / 6.6
/ AS6). P.11C develops the LIVE enabling of the existing detector plus one new live
behaviour: a detected cut stores its output WITH the checkpoint flag set, so the
cut becomes a recovery anchor. Goal (coordinator): "complete whatever it takes to
get scene detection and its associated logic developed and in place."

This is a wiring-and-compose phase (closer to K.1F than to the recovery arc).

2. WHAT THE DESIGNER BELIEVES ALREADY EXISTS (please CONFIRM or CORRECT each)
--------------------------------------------------------------------------------
From reading the committed source (src.zip). Designer's understanding:

2.1  TWO parallel pixel-processing entry points exist in cnr3_frame_processing.h:
       cnr3_process_caller_supplied_vapoursynth_frame_triplet
           (no scene-change; this is what the LIVE path calls today)
       cnr3_process_caller_supplied_vapoursynth_frame_triplet_with_scene_change
           (same args PLUS  const Cnr3SceneChangeConfig& scene_config)
     => The designer's read is that "enable detection live" may be as simple as
        switching the live call sites to the _with_scene_change variant and
        supplying a config -- NOT threading a new nullable param through the old
        one. CONFIRM whether the _with_scene_change variant is the intended live
        entry point, and whether the two should converge or stay separate.

2.2  Cnr3SceneChangeConfig (cnr3_frame_processing.h) is:
       struct Cnr3SceneChangeConfig {
           std::int64_t scene_change_threshold = 0;
           bool scene_chroma = false;
       };
     CONFIRM the meaning of scene_chroma (chroma included in the diff? a mode
     flag?) and what a sane default threshold is for 8-bit 4:2:0.

2.3  The detector cnr3_detect_scene_change_from_scalar_planes compares CURRENT
     source against PREVIOUS FILTERED output (previous_filtered_u/v) plus current
     vs previous DOWNSAMPLED luma, accumulates abs diffs into diff_total, sets
     scene_change = true when diff_total > scene_change_threshold. CONFIRM.

2.4  The RESET is already implemented in the caller: when scene_change is true the
     output chroma is a copy of CURRENT chroma (scene_change_reset_output_used),
     bypassing the recursive blend; else recursive_chroma_blend_used. CONFIRM the
     reset needs NO new work once detection is enabled.

2.5  Cnr3CallerSuppliedFrameProcessSummary ALREADY carries the result bits the
     store would need to read:
       scene_change_detection_used, scene_change_detected,
       scene_change_reset_output_used, recursive_chroma_blend_used,
       scene_change_threshold, scene_change_diff_total,
       scene_change_samples_examined.
     CONFIRM scene_change_detected is the authoritative "this frame is a cut" bit.

2.6  Cache-core ALREADY has the checkpoint store with promote-only semantics:
       store_checkpoint_owned_frame(...)  -- header says "eligible duplicate may
         promote an existing non-checkpoint slot to checkpoint" (this is CMS 6.6
         monotonic promote-only, flag-set inside the AS2 atomic).
       store_noncheckpoint_owned_frame(...)
     CONFIRM store_checkpoint_owned_frame is the correct primitive for a detected
     cut, and that its promote-only path matches CMS 6.6 (raise-only, never demote,
     inside the store atomic).

2.7  The live store WRAPPER cnr3_store_live_output_frame_for_authoritative_return
     (cnr3_arAllFramesReady.cpp ~411) does NOT currently take a checkpoint flag:
       cnr3_store_live_output_frame_for_authoritative_return(
           Cnr3FilterData& data, int frame_number, VSFrame* output_frame,
           const VSAPI* vsapi, const VSFrame*& out_return_frame,
           Cnr3Status& out_store_status, bool& out_returned_cached_winner)
     => The designer's read is that THIS is the real wiring gap for task B: the
        wrapper must learn the cut bit and route a cut to the checkpoint store /
        promote path. CONFIRM this is the right seam, and tell us the cleanest way
        to thread the cut bit in (extra param? a small store-request struct?).

2.8  The live path currently passes scene detection OFF: KDT shows
     p11c_called=0 scene_change_deferred=1 on every live branch (the live call uses
     the non-scene-change variant). CONFIRM.

3. THE THREE LIVE WIRING TASKS (designer's decomposition -- correct it if wrong)
--------------------------------------------------------------------------------
(A) Enable detection live: call the _with_scene_change variant (2.1) with a real
    Cnr3SceneChangeConfig, at the live compute sites, uniformly across branch-a/c/d.
(B) Thread scene_change_detected (2.5) into the store wrapper (2.7) so a detected
    cut routes to store_checkpoint_owned_frame (2.6), promote-only per CMS 6.6.
(C) Uniformity: (A)+(B) across branch-a/c/d together, identical handling regardless
    of which branch computed the frame.
(D) Reset is free once (A) is enabled (2.4).
Threshold source is an open parameter decision (plugin param / compile constant /
CMS default) -- see Q1 below.

4. THE QUESTIONS WE NEED YOUR READ ON (the two composition seams + parameters)
--------------------------------------------------------------------------------
These are the seams where "wire existing detection" meets "the recovery machinery
just built." We want your read on the ACTUAL code before any scope.

Q1. THRESHOLD SOURCE. Where should the live Cnr3SceneChangeConfig.scene_change_
    threshold come from -- a plugin parameter (rpGeneral-style), a compile-time
    constant, or a CMS-defined default? What is a sane default for 8-bit 4:2:0?
    And scene_chroma -- what should it be set to live?

Q2. CUT DETECTION INSIDE THE RECOVERY BRANCHES (seam 1). CMS 9.2 specifies per-hole
    detection during the ascending fill: "if a cut is detected at hole K, output[K]
    is computed as a fresh start ... stored WITH the checkpoint flag set ... the
    ascending walk continues." Two facts make this non-trivial:
      (a) the detector compares against the PREVIOUS FILTERED output, which in
          recovery is the RECONSTRUCTED predecessor (floor-fresh-start or prior
          hole-fill output);
      (b) recovery fills MULTIPLE frames per activation, ANY of which could be a cut.
    Questions:
      - In the live recovery fill loop, is each hole's compute already routed
        through the same pixel-processing entry point (so switching to the
        _with_scene_change variant enables per-hole detection uniformly)?
      - Does each per-hole store already go through a wrapper where the checkpoint
        flag can be set per hole, or is the checkpoint routing currently only at
        the final output[N] store?
      - Any concern with detection running against a reconstructed (rather than
        cache-resident genuine) predecessor? It should be fine (a reconstructed
        filtered frame is still a filtered frame), but confirm.

Q3. CHECKPOINT PROMOTION UNDER THE STORE ATOMIC (seam 2). CMS 6.6 requires the
    checkpoint flag-set to happen INSIDE the AS2 store atomic (never a separate
    lock), promote-only. D.5 proved a PINNED checkpoint survives a real prune pass.
    Questions:
      - When a recovery foundation/hole is BOTH pinned (recovery pin) AND a detected
        cut (checkpoint), do the flag and the pin coexist correctly on the same slot
        in the live store path? (D.5 suggests yes; confirm in the live store, not
        just the selftest.)
      - Does store_checkpoint_owned_frame's promote path compose with the recovery
        pin-record that the recovery store already does, under one atomic?

Q4. PROOF STRATEGY. Designer proposes synthetic footage with constructed cuts, like
    D.1-D.5: cut detected -> reset used (chroma = current, not blended) -> output[K]
    stored WITH checkpoint flag -> a later recovery finds it as an anchor. Likely a
    live-harness proof (like D.1-D.3) PLUS possibly a selftest for the promotion
    primitive (like D.4). Real-footage validation is DEFERRED to the later campaign
    (needs diagnostics + D-SUM-14). Does this proof shape match the code seams, and
    what golden values / KDT fields would you expect to assert on?
    (Note: at threshold tuning the recursive output moves ~1 LSB frame-to-frame, so
    the ROBUST proof is the KDT mechanism + direct byte checks, not a byte margin.)

Q5. fmParallel INTERLEAVING. CMS 6.6's whole rationale is out-of-order scheduling
    caching a frame non-checkpoint BEFORE its cut is detected, then promotion fixing
    it. The P.11C design note must carry an interleaving analysis showing the promote
    path is concurrency-correct (flag monotonic, set inside the atomic). Flag any
    live-path concern you see for that.
