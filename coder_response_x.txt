## Coder evaluation — CNR3_RIDER.option-error-messages

Designer scope reviewed:

```text id="hjxgct"
CNR3 — RIDER SCOPE: self-explanatory option error messages — v2
Baseline: committed CMS07-FEATURE.cnr2-descriptive-option-parser
```

### Verdict

```text id="nr8w4a"
APPROVED FOR IMPLEMENTATION AS A SMALL SOURCE RIDER
```

The scope is narrow, technically coherent, and suitable for a follow-up patch on top of the committed option-parser baseline. It improves user-facing diagnostics only: bad parameters already remain bad parameters; this rider makes the error messages more self-explanatory. The rationale is sound: users should see what they did wrong immediately, especially where values are computed or where a type error currently does not show what was received.

### Implementation interpretation

The rider changes the detail text built by the option parser’s error paths.

Current family:

```text id="dw80vj"
CNR3: invalid <option_name> option: expected ...
```

Target family:

```text id="ch6o49"
CNR3: invalid y_threshold option: got 256, expected an integer in the range 0.. ...
```

255 inclusive.
CNR3: invalid scene_threshold option: got 101.0, expected a finite float in the range 0.0..100.0 inclusive.
CNR3: invalid y_curve option: got "wobbly", expected exactly "wide" or "narrow".
CNR3: invalid scene_chroma option: got 2, expected 0 or 1.

````

This directly follows the required behaviour0L17-L24

### In-scope code work

Expected implementation work in `src/vapoursynth-Cnr3.cpp`:

```text id="pjfn9a"
1. Add shared expectation-text helpers for:
   - int 0..255 options
   - float 0.0..100.0 scene_threshold
   - curve string options
   - bool/int 0..1 scene_chroma

2. Update range/value error detail formatting:
   - int range: got <int64>, expected <expectation>
   - float range: got <%g>, expected <expectation>
   - curve value: got "<width-limited string>", expected <expectation>
   - bool value: got <int64>, expected <expectation>

3. Update typed-getter failures:
   - incorrect value type, expected <same expectation>

4. Keep all formatting snprintf-bounded.

5. Keep validation decisions unchanged.
````

The rider identifies the four value-error sites and states that those paths already hold the offendi0L27-L38 For type errors, the rider explicitly says not to invent a value; instead, emit “incorrect value type” plus the same allowed range/allowed-val0L40-L51

### Required helper discipline

I would implement the expectation text once per option kind and reuse it for both type errors and range/value errors.

Required message family:

```text id="3n8xli"
type error  : incorrect value type, expected <expectation>
range error : got <value>, expected <expectation>
```

That is preferable to hand-writing similar text at multiple sites, because the rider specifically requires the shared expectation text to prevent type-error and range-err0L53-L59

### Buffer-safety interpretation

The fixed buffers remain:

```text id="h9kfzo"
detail[128]
message[256]
```

The implementation must preserve bounded `snprintf` use. For curve-string echoing, the received string must be width-limited, for example `%.32s`, and a null pointer must be handled defensively. This is directly required by the rider’s curve-string and constraints 00L62-L67

### Stop conditions

Stop and report before expanding the patch if any of the following is discovered:

```text id="4kcux4"
1. Any invalid option is currently accepted.
2. Fixing the message requires changing validation logic.
3. A typed-getter failure path cannot be cleanly distinguished from a range/value failure.
4. VapourSynth does not preserve enough error context to produce the required one-line message.
5. Buffer-safe curve-string echoing cannot fit within the existing detail/message buffers.
```

If item 1 is found, that is not this rider. It is a parser validation bugfix.
